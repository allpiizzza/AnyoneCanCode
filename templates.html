범용 프롬프트 템플릿

오늘 배우는 건 코딩이 아니라 이 네 칸입니다

AI에게 "게시판 만들어줘"라고 하면 게시판 비슷한 게 나옵니다. 원하는 게 나오지 않는 이유는 대부분 AI가 부족해서가 아니라, 우리가 무엇을 원하는지 덜 말했기 때문이에요. 아래 네 칸을 채우는 습관만 들이면 결과물의 품질이 눈에 띄게 달라집니다.

빈칸 템플릿

그대로 복사해서 ○○ 자리만 바꿔 쓰세요. 오늘 쓸 모든 프롬프트가 이 형태입니다.

prompt-template.txt
[역할] 너는 ○○ 전문가야.

[상황/맥락] 나는 지금 ○○을 만들고 있어. 현재 상태는 이래:
(있으면 코드 / 에러 / 화면 상태 붙여넣기)

[요청] 내가 원하는 건 ○○이야. 구체적으로는 (기능/조건)을 해줘.

[형식] 결과는 ○○ 형태로 줘. (예: 전체 코드 파일로 / 단계별 설명으로 / 표로)

네 칸이 각각 하는 일

단계의미안 쓰면 생기는 일
[역할] AI가 어떤 입장에서 답할지 정해줍니다. "웹 개발자", "초등학생도 이해하게 설명하는 선생님"처럼요. 일반적이고 두루뭉술한 답이 옵니다.
[상황/맥락] 지금 뭘 만들고 있고, 어디까지 왔는지. 기존 코드나 에러 메시지를 그대로 붙여넣는 자리입니다. AI가 처음부터 다시 만들어버려서, 방금까지 잘 되던 것도 같이 바뀝니다.
[요청] 원하는 걸 한 문장으로. 그리고 구체적인 조건을 번호로 나눠서. 내가 상상한 것과 다른 게 나옵니다. 가장 흔한 실패 원인.
[형식] 결과를 어떤 모양으로 받을지. "전체 코드 파일로", "단계별로", "표로". 코드 조각만 와서 어디에 붙여야 할지 알 수 없습니다.
✱ 오늘 가장 많이 쓸 한 문장

"수정된 전체 코드로 다시 줘." — 비개발자에게는 "12번째 줄을 이렇게 고치세요"보다 파일 통째로 받아서 갈아끼우는 게 훨씬 안전합니다. [형식] 칸에 이 문장을 넣는 습관을 들이세요.

한 번에 다 시키지 말고, 쪼개서 시키세요

템플릿만큼 중요한 습관이 하나 더 있습니다. 요청을 작게 자르고, 하나가 끝날 때마다 화면을 확인하고 다음으로 넘어가는 것입니다. "게시판 만들고, 저장도 되게 하고, 배포까지 알려줘"를 한 프롬프트에 담으면 대부분 이런 일이 생깁니다.

  • 조건이 많아질수록 그중 몇 개는 빠집니다. 열 가지를 한꺼번에 시키면 여덟 개만 반영된 결과가 오는 식이에요. 그런데 뭐가 빠졌는지는 한참 뒤에 발견합니다.
  • 결과가 길어질수록 어긋난 곳이 생깁니다. 파일 세 개를 한 번에 새로 쓰면, 앞 파일에서 쓴 이름과 뒤 파일에서 부르는 이름이 서로 안 맞는 일이 흔합니다.
  • 무엇 때문에 깨졌는지 알 수 없습니다. 다섯 군데를 동시에 바꿨는데 화면이 하얗게 뜨면, 원인을 찾으려고 다섯 군데를 다시 뒤져야 합니다.
  • 되돌릴 지점이 없습니다. 조금씩 진행하면 "직전 코드로 돌아가면 되지"가 되지만, 한 번에 크게 바꾸면 돌아갈 곳이 없습니다.
✱ "AI가 집중력을 잃는다"는 표현에 대해

느낌으로는 딱 그렇습니다. 다만 실제로 벌어지는 일은 사람처럼 주의가 흐트러지는 게 아니라, 지켜야 할 조건이 많아질수록 그중 일부를 놓칠 확률이 올라가고, 답이 길어질수록 앞뒤가 어긋날 자리가 늘어나는 것에 가깝습니다. 대화가 길어지면 앞에서 정한 약속을 흘리기도 하고요. 원인이 무엇이든 대응은 같습니다 — 작게 쪼개고, 매번 확인하세요.

작업 리듬

  • 1

    한 번에 한 가지만 요청합니다

    "카드 색 바꾸고 정렬도 바꿔줘"가 아니라 "카드 색만 바꿔줘". 욕심나는 나머지는 메모해두고 순서대로 처리하세요.

  • 2

    결과를 화면에서 확인합니다

    코드를 읽을 필요는 없습니다. 브라우저에서 눈으로 보면 됩니다. 내가 부탁한 게 그대로 됐는지, 잘 되던 다른 부분이 망가지지는 않았는지 두 가지만 봅니다.

  • 3

    잘 됐으면 "여기까지 좋아"라고 알려주고 다음으로

    이 한마디가 다음 요청의 [상황/맥락] 역할을 합니다. AI가 지금 상태를 기준으로 이어서 작업하게 돼요.

  • 4

    망가졌으면 더 얹지 말고 되돌립니다

    고장난 위에 수정을 쌓으면 점점 걷잡을 수 없어집니다. 직전에 잘 되던 코드로 돌아간 다음, 요청을 더 잘게 잘라서 다시 시도하세요.

이어서 요청할 때 쓰는 문장

next-step.txt
지금 화면 잘 나왔어. 여기까지는 그대로 두고, 딱 하나만 더 할게.

[요청] (바꾸고 싶은 것 한 가지만)

나머지 기능이나 디자인은 건드리지 말고,
수정된 전체 코드로 다시 줘.
✱ 그렇다고 전부 쪼갤 필요는 없습니다

맨 처음 뼈대를 만들 때는 오히려 한 번에 크게 요청하는 편이 낫습니다. 오늘 STEP 1에서 화면 세 개를 한 프롬프트로 만드는 것처럼요. 쪼개기가 중요해지는 건 이미 만들어진 것을 고칠 때입니다. 잘 돌아가던 걸 지키면서 바꿔야 하니까요.

채워 넣은 예시

같은 요청을 템플릿에 넣으면 이렇게 됩니다.

example-filled.txt
[역할] 너는 초보자에게 친절하게 설명하는 웹 개발자야.

[상황/맥락] 나는 지금 독서모임 책후기 게시판을 만들고 있어.
HTML, CSS, JavaScript만 쓰고 있고, 아직 목록 페이지밖에 없어.

[요청] 목록 페이지의 각 카드에 마우스를 올리면
카드가 살짝 위로 떠오르는 효과를 넣고 싶어.
색이 갑자기 바뀌는 건 싫고, 부드럽게 움직였으면 좋겠어.

[형식] 수정된 CSS 전체 코드로 다시 주고,
어느 부분을 왜 고쳤는지 두세 줄로 설명해줘.
